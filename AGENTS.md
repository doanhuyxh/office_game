# OfficeHub

Văn phòng ảo 3D + quản lý nhân sự nội bộ cho một công ty (giao diện tiếng Việt, múi giờ `Asia/Ho_Chi_Minh`). Back-end ASP.NET Core (.NET 10, PostgreSQL, SignalR), front-end React 19 + Vite + TanStack + Three.js; package manager FE là **bun**.

## Luật không được vi phạm

1. **Kiểm tra quyền ở back-end** (`AuthPolicies.Hr` / `AuthPolicies.Manager`); manager chỉ thấy bản thân + cấp dưới (`GetSubordinateIdsAsync`). Guard/menu FE không phải lớp bảo mật.
2. **Ranh giới module**: module BE không tham chiếu project module khác — chỉ `OfficeHub.Modules.<X>.Contracts`; không JOIN / FK chéo schema. `dotnet test` (ModuleBoundaryTests) sẽ fail nếu vi phạm.
3. **Business logic đặt ở back-end** (endpoint/service/`Domain` của module). FE chỉ hiển thị, gọi API qua `services/api-client.ts`.
4. **`attendance.events` chỉ thêm, không sửa/xoá**; bảng công luôn tính từ sự kiện qua `TimesheetCalculator`. Đổi quy tắc tính → sửa cả `tests/OfficeHub.Modules.Attendance.Tests`.
5. **Thời gian do server quyết định** (`TimeProvider` + `Office__TimeZone`); lưu `DateTimeOffset` UTC.
6. **Không commit secret**: cấu hình qua `.env` (gitignore). Thêm biến → Settings có `ErrorMessage = "Thiếu X__Y trong .env"`, cập nhật `.env.example` + `commands.md`.
7. **FE**: ngoài feature chỉ import qua `@/features/<x>` — ngoại lệ: chỉ `routes/router.tsx` được import `@/features/<x>/page`; trang không export qua `index.ts`. Màn hình mới = feature + `page.ts` (export trang) + `page(...)` trong `routes/router.tsx`. Component trong feature: **mỗi component một thư mục kebab-case** `components/<ten-component>/index.tsx` (không file phẳng `components/Ten.tsx`) — chi tiết [.agent/frontend.md](.agent/frontend.md). Dùng helper sẵn có trước khi tạo mới. Chỉ dùng bun.
8. **Xong việc phải pass**: `backend/`: `dotnet build -warnaserror` và `dotnet test`; `frontend/`: `bun run build`; đổi `agent-runner/`: `bun run typecheck` và `bun test` trong đó. **Agent chạy qua bộ điều phối không được sửa `agent-runner/`** (runner + hook pre-push chặn).
9. **Đổi tool MCP phải cập nhật màn hình "Công cụ AI (MCP)"**: thêm / sửa / xoá tool trong `backend/src/OfficeHub.Mcp/Tools/*.cs` → cập nhật ngay catalog `frontend/src/features/mcp-tools/utils/catalog.ts` (tên, tiêu đề, mô tả, tham số, loại read/write/destructive, endpoint) cho khớp. Đây là màn hình tham chiếu "Công cụ AI (MCP)" (`/mcp-tools`, mọi nhân viên xem được), không tự suy ra từ code nên không được để lệch. Cập nhật luôn số lượng tool trong [.agent/business/mcp.md](.agent/business/mcp.md) và bảng nhóm tool [.agent/business/mcp-tools.md](.agent/business/mcp-tools.md).

## Giữ tài liệu đúng

- `.agent/` là nguồn sự thật duy nhất cho agent (`docs/ARCHITECTURE_V2.md` là kế hoạch, có phần chưa làm).
- Đổi business rule → sửa file trong `.agent/business/`; đổi schema → `database.md` / `database-workflow.md`; thêm lệnh/script/env → `commands.md`; đổi cấu trúc/luồng dữ liệu → `architecture.md`.
- **Đổi business rule → cập nhật luôn SRS trong Sổ tay dự án `TEST`** (cây trang "SRS OfficeHub", mục 1–11 theo nghiệp vụ), không chỉ sửa `.agent/`. Cách làm: `search_wiki` / `list_wiki_pages` dự án `TEST` tìm trang SRS của nghiệp vụ → `get_wiki_page` → `update_wiki_page` với `baseVersion` vừa đọc (báo người khác đã sửa → đọc lại, gộp, không ghi đè); chưa có trang cho nghiệp vụ mới → `create_wiki_page` dưới mục SRS phù hợp. SRS viết theo góc nhìn nghiệp vụ (ai làm gì, quy tắc, ràng buộc, trạng thái), không chép code / tên class. Trang bị khoá → không sửa, `comment_task` đề xuất nội dung + mention quản lý dự án. Làm cùng lúc với commit của task, ghi trong bình luận kết quả: đã cập nhật trang SRS nào (hoặc "không đổi business rule").
- **Thêm / sửa / xoá endpoint (REST `/api/*`, hub / route `/rt/*`, route `/mcp*`) → cập nhật luôn đặc tả API trong Sổ tay dự án `TEST`** (cây trang "API OfficeHub", mục 1–11 cùng số với SRS, mỗi nhóm endpoint một trang `n.k API …`). Ghi theo code: method, route, quyền / phạm vi dữ liệu, cột Token AI (đối chiếu `AccessTokenAuth.IsAllowed`), tham số, body + ràng buộc, phản hồi, lỗi riêng, tác dụng phụ. Đổi allowlist token AI → sửa cả trang "11.3 Allowlist route cho token AI (phụ lục)" và "11.4 Bảng route API" của SRS. Cách làm như SRS (`search_wiki` → `get_wiki_page` → `update_wiki_page` với `baseVersion`; nhóm mới → `create_wiki_page` dưới mục phù hợp + thêm dòng vào bảng trang con của mục). Làm cùng commit, ghi trong bình luận kết quả: đã cập nhật trang API nào (hoặc "không đổi API").
- Mỗi file ≤ ~8 KB, chỉ đọc file cần cho task; vượt thì tách theo domain con, thêm dòng vào bảng định tuyến (ở đây và `business/README.md`).
- Nếu tài liệu khác code, tin code và sửa tài liệu trong cùng commit.
- **Thêm / xoá sự kiện thông báo** (hằng `NotificationCategories`, nơi gọi `NotifyAsync`, phương thức `ITelegramWakeup`, `WebhookEvents`) → sửa danh mục `NotificationCatalog` trong cùng commit (tên, mô tả ai nhận / khi nào, nhóm, kênh, email, loại `target` được phép — `CategoryTargets`). `dotnet test` (NotificationCatalogTests) fail nếu lệch — [.agent/business/notifications-catalog.md](.agent/business/notifications-catalog.md).
- **Đối chiếu kế hoạch theo từng task**: khi làm xong một task (trước khi chuyển Chờ review), xem task đó có thuộc mục nào trong kế hoạch ở `docs/` (`BUSINESS_PLAN.md`, `ARCHITECTURE_V2.md`) không. Có → cập nhật mục đó cho khớp (đổi ⏳ → ✅, ghi trạng thái / phần còn lại, sửa lộ trình) **trong cùng commit** với task. Không thuộc kế hoạch → bỏ qua. Nếu thấy mục kế hoạch đã xong / đã bỏ mà vẫn ghi chưa làm, sửa luôn. Chỉ đánh dấu trạng thái mục kế hoạch; **việc còn lại / để sau ghi trên bảng dự án `TEST`**, không thêm danh sách tiến độ vào `docs/` hay `.agent/progress.md`. Ghi trong bình luận kết quả của task: đã đối chiếu kế hoạch, sửa mục nào (hoặc "không thuộc kế hoạch").

## MCP Tools: code-review-graph

**This project has a knowledge graph. Start with the code-review-graph
MCP tools to narrow scope, then read the source.** The graph is cheaper than scanning files and
gives you structural context (callers, dependents, test coverage) that file search cannot.

### When to use graph tools FIRST

- **Exploring code**: `semantic_search_nodes_tool` or `query_graph_tool` instead of Grep
- **Understanding impact**: `get_impact_radius_tool` instead of manually tracing imports
- **Code review**: `detect_changes_tool` + `get_review_context_tool` instead of reading entire files
- **Finding relationships**: `query_graph_tool` with callers_of/callees_of/imports_of/tests_for
- **Architecture questions**: `get_architecture_overview_tool` + `list_communities_tool`

### Verify in the source

- Narrow scope with the graph, then read the source. Do not change code from graph output alone.
- For any non-trivial change, read the implementation and the relevant tests before concluding.
- Verify the exact source when touching behavior, database logic, migrations, retries, fallbacks,
  recovery, or compatibility code.
- When the graph and the source disagree, the source wins. The graph may be stale or may not
  model that relationship.
- An empty graph result can mean "not indexed" or "not statically visible", not "does not exist".

### Key Tools

| Tool | Use when |
| ------ | ---------- |
| `detect_changes_tool` | Reviewing code changes — gives risk-scored analysis |
| `get_review_context_tool` | Need source snippets for review — token-efficient |
| `get_impact_radius_tool` | Understanding blast radius of a change |
| `get_affected_flows_tool` | Finding which execution paths are impacted |
| `query_graph_tool` | Tracing callers, callees, imports, tests, dependencies |
| `semantic_search_nodes_tool` | Finding functions/classes by name or keyword |
| `get_architecture_overview_tool` | Understanding high-level codebase structure |
| `refactor_tool` | Planning renames, finding dead code |

### Workflow

1. The graph auto-updates on file changes (via hooks).
2. Use `detect_changes_tool` for code review.
3. Use `get_affected_flows_tool` to understand impact.
4. Use `query_graph_tool` pattern="tests_for" to check coverage.
